# PostgreSQL migration foundation

## Scope and status

Celestin's local SQLite behavior is unchanged. `orbit.database.engine.connect()` continues to apply only its existing ordered SQLite migrations via `PRAGMA user_version`. The local `celestin`, `orbit`, and `memory-bridge` commands do not select PostgreSQL. The separate `celestin-hosted` command imports the optional PostgreSQL stack only when explicitly started; neither MCP runtime applies PostgreSQL migrations automatically.

The explicit `celestin-migrate` command applies packaged, ordered PostgreSQL SQL files. `0001_hosted_baseline.sql` is a separately versioned copy of the current hosted-schema draft for a **new, empty database**. Migration `0002_user_status.sql` additively adds human identity status with a `suspended` default and an `active|suspended` check; existing identities are not silently enabled. Migration `0003_retrieval_search_indexes.sql` adds partial GIN expression indexes for active message content and decision values using PostgreSQL's `simple` text-search configuration. Migration `0004_memory_capabilities.sql` adds default-deny project capabilities to human memberships and service grants: human memberships can carry candidate approval, conversion, history-read, and audit-read capabilities; service grants can carry conversion, history-read, and audit-read capabilities, while candidate approval remains human-only. Migration `0005_evidence_linked_memory.sql` persists the current manual `EvidenceLinkedMemoryStore` domain port with workspace/project foreign keys, verification/lifecycle fields, capture-provenance JSON, evidence ordering, and `TIMESTAMPTZ` operational timestamps. It is exposed only by the request-scoped PostgreSQL unit of work; it does not add Capture conversion, producer delivery receipts, immutable candidate revisions, approval events, durable Capture occurrence links, or hosted MCP runtime integration. These changes are additive; the runner has no automatic downgrade mechanism, so any production rollback procedure must be separately reviewed. These migrations remain a draft, are not approved for production use, and should only be applied after the team approves the target schema. The source draft at `docs/hosted-tenancy-schema.sql` remains unchanged and is not executed by this runner. Once applied anywhere, a migration file is immutable: make schema changes in a new numbered file.

Migration `0006_candidate_revision_store.sql` adds project-scoped producer and source-namespace registry rows; candidate identities and sequential immutable revisions; append-only approval/rejection/revocation events; candidate evidence records; zero-based ordered occurrence links that can share an evidence record; and an immutable conversion-ledger row linked to the existing knowledge record. Migration `0007_memory_request_rls.sql` extends forced RLS to the existing `chat_messages` and `project_memory` tenant tables. Migration `0008_project_scoped_runtime_roles.sql` replaces the legacy caller-settable-GUC policies on all twelve tenant-content tables. It adds a protected `celestin_private.project_runtime_scopes` map from each database login to exactly one workspace/project, and scope helpers derive identity from PostgreSQL `session_user`. Migration 0008 expects the three non-login group roles to be provisioned out of band and never creates or drops roles. `PostgresRequestUnitOfWork` borrows the already authorized project login's request connection; its adapters do not open independent connections or finalize the transaction.

### RLS policy inventory and trust boundary

This inventory is derived from the packaged migration definitions; no live PostgreSQL catalog was inspected during this review. Migrations 0006–0007 enable and force RLS on each listed content table. Migration 0008 removes the old named policies and installs one policy for the `celestin_project_runtime` group on every table. Its `USING` and `WITH CHECK` clauses call `public.celestin_request_scope_matches(workspace_id, project_id)`; that helper checks the row against the protected mapping for `session_user`.

| Migration | Tenant-content tables protected by the policy |
| --- | --- |
| `0006_candidate_revision_store.sql` | `celestin_knowledge_records`, `celestin_evidence_records`, `celestin_project_producers`, `celestin_project_source_namespaces`, `celestin_candidates`, `celestin_candidate_revisions`, `celestin_candidate_review_events`, `celestin_candidate_evidence_records`, `celestin_candidate_occurrences`, `celestin_candidate_conversions` |
| `0007_memory_request_rls.sql` | `chat_messages`, `project_memory` |
| `0008_project_scoped_runtime_roles.sql` | Replaces the GUC policies on all twelve tables above; adds the protected login-to-project map, role-specific authorization-table policies/grants, and authorization advisory-lock functions/triggers. |

The old policies in 0006–0007 compared row scope to caller-settable settings named `celestin.workspace_id` and `celestin.project_id`. Migration 0008 drops those named policies before replacing them, because PostgreSQL permissive policies combine with OR. The replacement helper reads `celestin_private.project_runtime_scopes` for the authenticated `session_user`; the application does not set a trusted scope GUC. Each project login maps to exactly one workspace/project. The request factory does a preliminary authorization lookup through a read-only authorization identity, selects a server-configured project pool, then rechecks authorization and validates the login mapping inside the project transaction before running protected handlers.

Migration 0008 also enables RLS on the authorization tables. The authorization-reader group has SELECT through a read-only policy; the authorization-admin group has the separately granted administrative policy. The project-runtime group can read only authorization rows relevant to its mapped project/workspace, and has no access to the schema-migration ledger or the mutable mapping table beyond SELECT of its own login row. Runtime connections never receive the migration credential.

**Security boundary and residual trust:** a project-specific login can access only the project named by its protected mapping, even if SQL omits tenant predicates or sets the old `celestin.*` settings. Project logins are non-superusers, have `NOBYPASSRLS`, do not own protected tables/schemas, are members only of the project-runtime group, and cannot modify mappings or switch into another project's login. The central application and credential-management authority remain trusted: a compromised application process or control credential could choose another already-configured project DSN. RLS does not protect against superusers, migration/database owners, `BYPASSRLS` roles, or compromised central credential management. The project-specific login limits the blast radius of one leaked project credential; it does not remove those residual trust assumptions.

Migration 0006 intentionally has no delivery receipt or delivery-ID uniqueness table because the separately versioned delivery/revision payload-equality profile remains unresolved in `docs/delivery-contract-decision-audit.md` (D-08). The exact compared fields, normalization, explicit-null-versus-omitted behavior, equality profile/version, and receipt shape remain undefined; the approved conversion-payload hash must not be reused for delivery equality. Its conversion-ledger schema does not implement conversion, replay arbitration, or persistence of the approved conflict-edge/pending-endpoint and audit-event graph. Producer registration lifecycle, authorization-epoch/revocation mutation handling, and the authenticated producer ingress are also not implemented here. These migrations have only scripted/static coverage; none has been executed or syntax-checked against a PostgreSQL server. The migration runner has no automatic downgrade mechanism; any future rollback procedure must be separately reviewed.

The separate `celestin-hosted` command composes Auth0-verified Streamable HTTP with PostgreSQL when explicitly configured. It routes only to a server-configured pool keyed by a resolver-issued workspace/project pair and performs final authorization on that project's database identity. Local stdio remains SQLite-backed. Hosted deployment is still disabled until the live security gate and separate release approval pass. `PostgresEvidenceLinkedMemoryStore` implements the manual Evidence/Knowledge port on the request connection, but it is not exposed through the hosted MCP tools; Capture conversion, delivery receipts/replay, and the approved conflict/audit graph remain outside this runtime. Live cases for migrations 0005–0008, role separation, direct SQL, authorization, RLS, and Evidence storage are defined in `tests/postgres/test_live_authorization.py` and `tests/postgres/test_live_evidence_store.py`; they have not been executed against PostgreSQL here. The hosted schema also does not enforce the last-active-workspace-owner policy by itself.

## Separate migration, control, and project roles

Migration 0008 expects these pre-provisioned **NOLOGIN group roles** and never creates or drops database roles:

- `celestin_project_runtime` — minimal tenant-content privileges used only by project-specific logins.
- `celestin_authorization_reader` — read-only authorization lookup and request-lock privileges.
- `celestin_authorization_admin` — controlled mutation of authorization rows and project-login mappings.

Each role must be a non-superuser, `NOBYPASSRLS`, `NOCREATEROLE`, `NOCREATEDB`, `NOREPLICATION`, and `INHERIT`, with no role memberships that grant a path to other roles. Migration 0008 refuses unsafe or missing group roles. Provision the group roles and create separate login roles outside this migration under a separately controlled operator workflow. Never give a project login role ownership of protected tables or either schema, public/private schema `CREATE`, or a path to another project's login.

The explicit `celestin-migrate` command alone uses the migration/schema-owner DSN (`CELESTIN_POSTGRES_DSN` by default). The hosted runtime does not use that variable and has no fallback to a shared content credential. It requires a read-only control login in the authorization-reader group and a separate login per configured project, each mapped in `celestin_private.project_runtime_scopes` to exactly one `(workspace_id, project_id)`. The mapping row uses PostgreSQL's authenticated `session_user`; application-provided settings, MCP arguments, or `current_user` after role switching do not determine the scope. The administrative registry can insert/delete mappings but cannot create roles, store secrets, or rotate credentials. A database operator must provision each project login as a member only of `celestin_project_runtime`, grant the narrow group privileges, store its secret outside the repository, register its scope through the trusted admin path, and validate the mapping before enabling its pool.

Hosted configuration uses `CELESTIN_POSTGRES_AUTHORIZATION_DSN`, `CELESTIN_HOSTED_PROJECT_DSN_ENV_MAP` (a JSON mapping of canonical `workspace-uuid/project-uuid` keys to server-side `CELESTIN_PROJECT_POSTGRES_DSN_*` variable names), and `CELESTIN_HOSTED_PROJECT_ROLE_ISOLATION_ENABLED=true`. Each referenced DSN must be held in the deployment's managed secret source. A fixed maximum of 32 configured project pools and two connections per project pool bounds initial cohort resource use; the control pool is separately bounded. If a project is authorized but absent from this static server mapping, the request fails closed. Startup verifies direct-login identity, least-privilege role attributes/memberships, exact mapping to the configured scope, RLS state/policy and required grants, and refuses readiness if the checks fail. Hosted runtime remains disabled until live security validation and release approval; setting this flag alone is not approval to deploy.

The authorization reader and project logins are deliberately separate. Project logins can read authorization rows only as needed for their one project and cannot read the migration ledger or mutate the mapping. The authorization reader has no tenant-content table access. The admin login is used only for trusted provisioning/revocation operations and must not be exposed to request handlers. The migration role is not a runtime role. Live integration tests use five distinct, pre-provisioned logins (migration, admin, authorization reader, project A, project B), require one fresh loopback disposable database, and verify each role's identity and group membership before migrations. The live suite also attempts cross-project SQL, legacy-GUC forgery, role switching, mapping writes, and unfiltered queries under both project logins. These cases have not been run in this checkout; static/scripted tests do not establish PostgreSQL catalog, policy, or lock behavior. The central application and its credential-management authority remain trusted; a compromised application process could select another server-configured project's credential. Protecting against that compromise requires a stronger boundary such as separate application deployments or databases.

Authorization requests hold shared transaction-scoped advisory locks for the workspace and principal. Authorization changes and project-login mapping changes take the matching exclusive advisory locks through database triggers and the trusted provisioning service. This allows an already authorized transaction to finish before a concurrent revocation commits; later requests deny. The old test claim based on row-level `FOR SHARE` is superseded. Live lock/race tests remain required.

## Install and explicitly initialize a new database

Install the optional driver extra in the environment used for administration:

```powershell
python -m pip install -e ".[postgres]"
```

Provision a dedicated PostgreSQL database first. Supply its DSN to the command through the operator's approved secret manager or secure local environment setup; do not put credentials in the repository, command-line arguments, logs, or checked-in configuration. The command reads `CELESTIN_POSTGRES_DSN` by default and accepts `--dsn-env NAME` to use another environment variable name.

```powershell
# Set CELESTIN_POSTGRES_DSN from your approved local secret source.
celestin-migrate
```

On success, the command prints the migration version and applied versions, not the DSN. It acquires a PostgreSQL session advisory lock. When no ledger exists, it first checks for user schemas, table/view/sequence/foreign-table relations, procedures, and user types without excluding ledger-named objects. It then creates `public.celestin_schema_migrations` and performs a second check. PostgreSQL creates a composite row type and associated array type for a table ([type catalog](https://www.postgresql.org/docs/18/catalog-pg-type.html), [type system](https://www.postgresql.org/docs/18/extend-type-system.html)). The second check ignores only the ledger table and the exact array type identified through that row type's `typarray` OID; unrelated relations and types still cause a refusal. It then applies each pending migration and its ledger row in one transaction with the migration schema pinned to `public`. If a populated ledger already exists, versions and SHA-256 checksums are checked before pending migrations run. A pre-existing empty ledger is ambiguous and is refused rather than adopted. The ledger records `version`, `name`, `checksum`, and the server-side `applied_at` timestamp.

Migration DDL must be transactional. A failed migration rolls back its own DDL and ledger insert; earlier successful versions remain recorded and may be resumed after the cause is corrected. The initial ledger creation commits before version 1 starts, so a failure before any migration is recorded can leave an empty ledger. Do not rerun against or manually adopt that database; preserve it for inspection and ask the database owner to provision a new disposable database for a later authorized attempt. The session lock is released when the runner exits. Do not edit an applied migration to repair it: restore the exact original file and add a new migration for a forward correction.

## Existing databases without a ledger

The runner fails closed if it finds user objects but no Celestin ledger. It does not infer that an existing schema matches the baseline, create a ledger over it, or attempt adoption. In particular, do not point it at `celestin_schema_test_v2` or another database where the hosted schema was applied manually. First take a verified backup, inspect the complete schema and data, and prepare a separately reviewed adoption procedure that compares every object and records the exact baseline checksum. That adoption procedure is not implemented here. Until then, use only a newly provisioned empty database for initialization.

## Tests and verification boundary

`tests/postgres/test_migration_runner.py` uses an in-memory fake connection to check ordering, checksum drift, repeat application, refusal of untracked objects, rollback behavior, and serialization logic. `tests/postgres/test_migrate_cli.py` checks the missing-DSN path. These fake tests do not establish that PostgreSQL accepts the SQL or that row/advisory locks behave as intended on independent real sessions. The explicitly opted-in live test procedure, target safeguards, commands, and limitations are documented in [PostgreSQL integration tests](postgres-integration-tests.md). It applies migrations only to one pre-provisioned fresh disposable database and does not drop or truncate it.

No SQLite rows are imported. A separate import design must resolve legacy SQLite integer-ID collisions, tenant/project mapping, timestamp/time-zone backfill, source-message links, and rebuildable FTS/vector/PageIndex indexes before any data transfer is attempted.
